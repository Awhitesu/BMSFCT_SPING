# E2实体USB在位检测（2026-10-18）

第一轮修复仅分离了工具状态和连接显示，`connect()`仍把CLI版本检查成功作为返回True的条件。因此实体E2未接入时，初始化仍可能完成。本轮修正实际判定，不再只修改显示。

## 当前判定

1. 检查本机`rfp-cli`是否可运行，记录`tool_ready`。
2. 使用Windows SetupAPI读取**当前在位**的USB节点，排除仅安装过驱动、已拔出的历史设备。
3. 精确匹配瑞萨E2的硬件标识`VID_045B&PID_82A1`，并检查节点已启动、没有驱动问题码。E2 Lite的`82A0`和IE850A的`0250`不会被误认为E2。
4. 工具可运行且识别到可用的实体E2，初始化才返回True。未插入、禁用、驱动异常或枚举失败均不通过。

硬件标识依据本机瑞萨官方驱动安装文件，两种驱动均使用相同映射：

- `C:\Program Files (x86)\Renesas Electronics\MCU Tools Drivers\E2_E2LITE\E2usb_x64.inf`
- `C:\Program Files (x86)\Renesas Electronics\MCU Tools Drivers\E2_USB_WINUSB\E2usb_x64_winusb.inf`

SetupAPI使用`DIGCF_PRESENT | DIGCF_ALLCLASSES`和USB枚举器。[微软接口说明](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdigetclassdevsw)明确`DIGCF_PRESENT`只返回当前在位设备。通过[设备节点状态接口](https://learn.microsoft.com/en-us/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_get_devnode_status)读取启动状态和问题码。

没有采用CLI工具类型列表中出现“e2”就算接入的方式：本机无实体E2时，`rfp-cli -d RH850 -list-tools`仍输出E2、E2 Lite等类型名，不能据此认定硬件在位。

## 显示和操作

| 情况 | 初始化 | 硬件管理 | E2调试页 |
| --- | --- | --- | --- |
| CLI可用但未接E2 | 失败 | 红色“离线”，附未检测到E2原因 | 红色“E2未连接”，禁止烧录 |
| E2被识别且驱动正常 | 完成USB识别 | 黄色“E2已识别（目标未验证）” | 黄色“E2已识别” |
| 节点禁用或驱动异常 | 失败 | 离线并提供问题码 | 禁止烧录 |
| 系统枚举出错 | 失败 | 离线并提供检测失败详情 | 不显示已识别 |

初始化日志在没有E2时输出：

```text
[!] e2_rfp: offline (未检测到瑞萨E2 USB设备，请检查USB连接和E2供电（工具已就绪）)
```

识别到E2时输出“E2 USB已识别；目标连接未验证”。USB在位不等于目标MCU握手成功，仍不显示目标“已连接”。

调试页“检测E2”按钮、后台轮询和硬件管理后台状态刷新会重新检查USB在位。拔出后清除旧成功标志；重新接入后可恢复USB识别。界面轮询使用已有的`DeviceTask`机制，避免在GUI线程枚举；驱动忙时不等待其锁。

自动化工步的“连接检测”现在会检查实体E2，未接入时返回失败。状态查询、烧录、校验和回读也会检查在位，不能仅凭旧的工具就绪标志继续。已有Ready/Busy/Pass/Error/Lost状态名称和烧录最终PASS判定保持兼容。

## 本机实测

本机没有E2 USB设备时，调用实际安装的RFP V3.24和实际Windows设备枚举，得到：

```text
init_success: false
tool_ready: true
usb_connected: false
presence_checked: true
status: 离线
```

一次USB枚举约15毫秒；本次E2初始化约0.203秒。这是当前机器的单次测量，不是所有机器的速度保证。

[实际初始化记录](../logs/e2_usb_presence_actual_20261018.json)保留了完整结果和日志。检查只读Windows设备树，没有打开E2控制接口，没有连接、复位、供电、擦除或烧录目标MCU。
