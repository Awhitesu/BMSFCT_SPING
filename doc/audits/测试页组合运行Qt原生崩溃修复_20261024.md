# 测试页组合运行Qt原生崩溃修复

## 结论

测试页关闭后只隐藏，没有建立完整的GUI删除生命周期。下一页后台任务触发Python循环垃圾回收时，旧页面及其Qt对象进入Shiboken的主线程延迟删除路径，随后在QObject析构中触发C++纯虚函数调用并中止进程。

此次修复明确关闭页面的删除时机：先取消UI任务与刷新，在GUI事件循环中销毁；在DeferredDelete真正执行前保留页面包装对象，收到destroyed后解除保留。没有关闭垃圾回收，没有按单个测试隔离来代替组合验证。

## 原生证据与对照

- 当前环境：Python 3.14.0，PySide6、Shiboken、Qt均为6.10.3。此次没有修改依赖版本。
- 原9项测试组合可复现进程异常退出，普通复现退出码3。日志与汇总：`logs/qt_recipe_selection_20261024_baseline/`。
- 仅在诊断子进程安装CRT SIGABRT处理器，使用RtlCaptureStackBackTrace与DbgHelp记录实际原生调用链：`Py_HandlePending → Shiboken::BindingManager::runDeletionInMainThread → QtWidgets包装对象析构 → QObject::~QObject → purecall → abort`。该钩子改变最终退出码，未加入生产程序，也未用于最终通过验证。
- Qt6Core中直接调用者为`QObject::~QObject+0x866`，RVA为`0xEDAE6`。这是析构路径，不是仅凭Python堆栈中configparser/INI调用位置推断的配置故障。原生记录：`scratch/qt_recipe_gc_20261024/abort_stack.json`；复现输出：同目录`capture.log`。
- 对照实验：只移除事件过滤器仍崩溃，只移除滚动条lambda仍崩溃；在GUI中明确销毁关闭页面后组合运行通过。仅设置WA_DeleteOnClose、却不保留待删除包装对象，在原手动processEvents清理方式下仍可崩溃；加入待删除对象保留直至destroyed后，原清理方式组合连续5轮通过。
- Shiboken 6.10.3的对应源码确实将待处理C++析构项交由主线程执行：[bindingmanager.cpp](https://github.com/pyside/pyside-setup/blob/6.10.3/sources/shiboken6/libshiboken/bindingmanager.cpp)。Qt要求QObject删除遵守所属线程与事件生命周期：[QObject文档](https://doc.qt.io/qt-6.10/qobject.html)。

## 修改

- `OverviewTab.closeEvent()`调用原有取消与收尾逻辑，使用WA_DeleteOnClose在GUI事件循环中销毁页面。
- 在实际销毁前由应用保留已关闭页面，destroyed时释放，防止手动事件泵或后台循环回收抢先处理Python包装对象。
- 关闭时停止列宽、刷写显示和滚动刷新，并移除视口事件过滤器。
- 列宽与刷写状态的延迟刷新改成页面所属的单次QTimer；关闭后停止、删除页面时随父对象删除，槽函数也检查关闭状态。
- 新增压力回归曾明确暴露：页面删除后，旧singleShot列宽回调还访问已删除TestSequenceTree。上述定时器修复解决了该路径。
- 测试夹具处理DeferredDelete并验证页面实际销毁，模拟真实app.exec()中的删除流程。另保留一份使用原清理方式的组合对照，验证源码修复不依赖夹具变化。
- 保留此前ZLG连接复用、上位机就绪即继续以及正常调用`--shutdown`的行为。
