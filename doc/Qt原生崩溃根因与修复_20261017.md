# Qt原生崩溃：PYSIDE-3246根因及修复

## 已确认的故障

本轮不再仅依据“某个Python测试附近崩溃”推断原因。旧运行库复现后取得本地原生转储，并对异常上下文、直接返回地址和对应版本源代码进行核对。

原环境为Python 3.11.9、PySide6/Shiboken 6.10.1。项目虚拟环境此前继承了全局Qt库；本地VS Code调试配置另有多个配置直接写死全局Python。

### 原生现场

- 异常：`0xC0000005`，异常参数`[8, 0]`，即尝试从空地址执行指令。
- RIP和RAX均为0，直接返回地址落在`shiboken6.abi3.dll!Sbk_GetPyOverride+0x93`。
- RCX为`0x7fffd9e0ed08`，与该进程Python DLL导出的`_Py_NoneStruct`地址相等。
- 对应虚方法名称为`disconnectNotify`。
- 反汇编显示，描述符辅助函数取`Py_tp_descr_get`（槽号54）后尾调用返回地址。`NoneType`没有该描述符函数，返回0，随后跳转空地址。
- 保存的其他栈地址仅是候选地址扫描，不冒充完整符号展开；上述直接调用者来自原始RSP处返回地址。

### 与官方修复逐项对应

6.10.1的`Sbk_GetPyOverride`在取得GIL之前检查缓存是否为`Py_None`；等待GIL期间，另一个线程可能已把同一缓存设置为`Py_None`。原实现取得GIL后仅判断缓存是否非空，于是把`Py_None`作为方法描述符处理，发生此次空调用。

6.10.2源代码在`gil.acquire()`之后增加第二次`resultCache == Py_None`检查，注释明确标注PYSIDE-3246。Qt官方发布说明也明确指出：已修复多个线程同时检索同一个方法重载时的崩溃。原生现场、反汇编和官方源代码与该竞态一致，支持将此次空地址故障归因于PYSIDE-3246。

资料：

- [Qt官方Shiboken发布说明：6.10.2 / PYSIDE-3246](https://doc.qt.io/qtforpython-6.10/release_notes/shiboken6_release_notes.html)
- [6.10.1官方源码](https://github.com/pyside/pyside-setup/blob/6.10.1/sources/shiboken6/libshiboken/basewrapper.cpp)
- [6.10.2官方源码](https://github.com/pyside/pyside-setup/blob/6.10.2/sources/shiboken6/libshiboken/basewrapper.cpp)

## 修改

1. `requirements.txt`固定PySide6为6.10.3，保留同一6.10系列的补丁升级。
2. 在项目`.venv`内安装一致的PySide6、Essentials、Addons和Shiboken 6.10.3。已检查模块路径和实际Qt版本；全局Python仍为6.10.1，未修改其他项目运行库。
3. `main.py`在登录及设备初始化之前核对绑定、Shiboken和Qt版本。旧版本或混合版本会明确报错并给出项目虚拟环境的启动方式；启动日志记录实际版本与Python路径。
4. 本地`.vscode/launch.json`的5个配置统一使用`${workspaceFolder}/.venv/Scripts/python.exe`。该目录原本未跟踪进仓库；其他电脑应按README创建并安装项目虚拟环境。源代码启动检查仍可阻止错误环境启动。
5. 增加运行库版本检查测试，并保留原生现场抓取、分析和压力测试工具。本轮没有继续通过改动业务线程时序来掩盖崩溃。

本结论针对取得原生现场的PYSIDE-3246故障，不宣称所有潜在原生崩溃永久消失。此前日志中其他地址的故障没有各自完整转储，不将它们未经验证地全部归为同一个原因。未连接实际仪器，未打包或推送GitHub。请结束旧软件进程后，重新使用项目虚拟环境启动。

## 后续复验方法

从项目根目录运行：

```powershell
.\.venv\Scripts\python.exe tools/qt_crash_stress.py --runs 10 --timeout 180 --output logs/qt_recheck
```

该入口使用 offscreen Qt 和测试替身，不连接真实仪器。每轮独立进程，正常垃圾回收，记录测试起止位置、退出码和逐轮汇总；遇到失败立即停止，不能把仅打印了测试通过但进程退出异常的轮次算为通过。

如出现新的访问冲突，可附加 `--native-dump`，需要本地 `tools/native_debug/procdump64.exe`。诊断钩子只在测试子进程显式启用，未加入生产启动路径。该模式会改变异常处理时序，常规回归仍使用不带钩子的方式。转储含进程内存，仅保留本地；分析工具的可选依赖也不进入应用运行依赖。
