# 新增能力架构可行性审查

审查日期：2026-10-14。范围：现有源码，以及前一份功能差距审查建议增加的能力。本次为静态架构审查，没有修改运行逻辑，也没有执行现场设备操作。

## 结论

现有架构具备扩展基础，适合增量改造，不需要整体重写。但不能把所有能力继续塞入现有执行引擎。增加设备动作、报表格式可以沿用现有基础；条件分支、循环、子序列、断点调试、可靠停止和完整清理，需要先改造执行与结果模型。

| 要增加的能力 | 当前基础 | 可行性与前置工作 |
|---|---|---|
| 更多设备及测试动作 | devices 驱动、device_steps 字段与动作定义 | 可扩展；先统一动作标识、超时、结果与设备访问入口 |
| Excel 点位、组合设备映射进入自动测试 | 已有 EASY320 点位导入、电阻板组合通道 | 需要共享映射服务；调试与自动化目前尚未完全共用 |
| 初始化前检查 | 配方与硬件配置已存在 | 可增加独立校验器，检查动作、参数、通道、启用设备和资源冲突 |
| HTML/PDF 报表、历史查询与统计 | SQLite 与 Excel 记录 | 可扩展；完整追溯需补运行标识、原始值、版本和附件字段 |
| 配方版本、发布、比较与运行快照 | JSON 配方、部分备份与差异工具 | 局部改造；增加稳定 ID、版本和原子保存，运行使用不可变快照 |
| 条件、循环、子序列调用 | 固定测试项与工步列表 | 先改执行模型，不能仅新增几个枚举或按钮 |
| 断点、单步、变量观察 | 工步索引、变量字典、挂起标志 | 先增加执行状态机、调用栈和安全暂停边界 |
| 全设备资源调度 | 部分引擎锁、device_step_lock | 需要统一设备所有权；调试与序列必须使用同一仲裁入口 |
| 停止、异常清理与恢复 | stop、safe_shutdown_outputs | 先改取消与清理机制；当前不保证非阻塞或完整收尾 |
| PLC 状态机、MES 重试与防重复提交 | 已有 PLC/MES 接口 | 接口可复用；可靠流程需要独立状态机、持久化发送队列和幂等键 |
| 插件、仪器校准和资产管理 | 驱动分目录、动作元数据 | 可逐步建立接口；目前还不是可独立加载的插件体系 |
| HIL/MIL 等集成 | 通讯与设备基础 | 尚不足以直接支持；需另行定义适配接口与具体需求 |

## 已有的可复用基础

- `core/device_steps.py` 已把新设备动作、字段、参数校验从主引擎中部分分离，可作为动作注册体系的起点。
- `ChannelWorker` 与 `ui/device_task.py` 已有后台执行和信号回传，可继续用于界面与操作执行的分离。
- `devices/manager.py` 已提供集中驱动管理与部分锁机制，可演进为统一设备服务。
- SQLite 已有写入队列和测试记录，适合通过数据库迁移扩充，而非丢弃历史数据重建。

这些基础支持改造，但后台线程、动作元数据和驱动目录本身，并不等于已具备统一取消、调度或插件能力。

## 必须先处理的结构问题

### 1. 执行模型依赖固定索引与名称

`core/engine.py:52` 的 SubStep 与 `:59` 的 TestStep 是固定列表模型；执行通过 current_step_index/current_sub_step_index 推进。`start_channel_test`（:2532）还根据中文类型、设备名称和参数字符串推断动作类型。

部分结果以测试项名称作为字典键（:188、:2194）。同名测试项、循环重复执行和子序列调用将难以区分结果，不能直接用名称作为执行身份。

建议引入稳定 step_id、execution_id、attempt、循环序号及调用路径。内部支持条件、循环和调用节点；现有两级编辑界面可以继续保留，以表单或子序列引用编辑复杂节点，不要求界面出现无限层级。

### 2. 动作保存使用显示文字

`core/device_steps.py:225` 的新格式保存中文设备名、动作名和字段名，`:235` 再按显示文字恢复。修改名称存在旧配方无法匹配的风险。

持久化应保存稳定 device_type/action_id/参数键和 schema_version，中文名称仅用于显示。保留现有两种格式的读取适配器，避免升级后已有配方失效。

### 3. 停止路径仍可能阻塞或竞争

`execute_sub_step`（engine.py:1936）同步执行设备动作。`stop_channel_test`（:2736）直接调用 worker.stop，随后等待线程最多 2 秒；worker.stop 又会进行输出关闭和记录收尾。若入口来自界面线程，这些操作仍可能阻塞界面。超时保留线程引用可以避免线程被提前销毁，但不代表动作已停止。

直接跨线程调用 stop 也意味着清理可能与正在执行的动作并行发生。现有取消回调能覆盖部分动作，但没有全设备一致的取消与截止时间。`DeviceTask.shutdown` 使用无期限 wait，同样需要明确收尾策略。

建议使用线程安全取消令牌，界面只发出取消请求；执行侧在协议超时和动作边界检查取消，统一转入 Cleanup。任务结束后才释放设备所有权。阻塞式驱动必须有有限超时，不能仅依靠 QThread.quit。

### 4. 调试与自动化不是同一个设备访问体系

BoardDebugTab 和 ResistorBankTab 自行创建 RNBoard；自动化由 manager.get_rn_board 创建并缓存另一组实例。因此同一设备可能有不同连接与不同锁。

EASY320 的导入点位、组合电阻卡全局通道也尚未完整贯通旧自动工步。建议统一 DeviceHub 与 ChannelMap，按物理设备标识管理连接、通道映射、互斥和占用提示；调试页与测试工步均调用该服务。

### 5. 结果模型不足以支撑可靠追溯

动作返回值混合 PASS 字符串、数值和 MeasurementValue；引擎还会从多个子工步中选择用于最终判定的值。数据库以标量结果为主，没有完整的工步执行身份、尝试次数及附件关联。

此外，现有部分 CSC/NTC 路径包含异常值替换与随机补偿。应将原始读数、计算值和仿真值明确分开，不能让替换值掩盖设备原始异常。

建议统一 StepResult：执行状态、判定结果、raw_value、derived_value、单位、错误、起止时间、执行身份及附件。控制成功与测量合格分别记录，避免靠任意返回字符串解释两种语义。

### 6. 清理与记录成功缺少统一确认

manager.safe_shutdown_outputs（:405）覆盖部分输出，但模拟器只按当前测试通道关闭，未统一纳入所有板卡和本次运行实际占用的输出。关闭连接与关闭电气输出也应区分。

DB 的明细写入是异步任务；finish_test 的同步队列操作能等待前序队列处理，但不证明此前所有异步插入都成功。需要记录写入失败状态、明确 flush 确认和报告生成失败的处理方式。

建议建立运行资源清单与 Setup/Main/Cleanup 生命周期，按运行所有权收尾，避免关闭另一运行使用的共享设备。报告服务从结果存储生成，界面和执行线程不承担长时间导出任务。

## 推荐的增量实施顺序

1. **稳定数据身份与映射**：配方版本、稳定动作/工步 ID、运行快照、统一通道映射；保留旧配方适配器。
2. **统一执行边界**：ExecutionContext、取消令牌、超时、结构化结果、设备资源所有权与 Cleanup。优先消除界面同步等待和跨线程直接收尾。
3. **增加高级序列能力**：条件、循环、子序列、局部变量、断点与单步，逐步替换大段字符串分派。
4. **完善产线追溯**：预检、配方发布、报告、历史统计、审计，以及 PLC/MES 可靠状态流转。

不建议同时重写所有驱动和页面。先把现有操作包成统一处理器，保持现有配方行为，再逐设备收敛接口。

## 改造验收重点

- 同名测试项、循环与子序列每次执行均有独立结果。
- 修改中文显示名后，旧配方仍能加载并执行。
- 调试和自动化访问同一设备时不会交叉发送或抢占输出。
- 设备无响应时有明确超时；停止操作不阻塞界面，清理不会与原动作竞争。
- 清理覆盖本次运行拥有的输出，不影响其他运行。
- 原始异常值被保留；仿真或补偿数据可识别，判定来源可追溯。
- 数据库写入失败可见，报告不会静默缺失结果。
- 旧配方的执行顺序、PASS/FAIL、单位和附件在迁移前后保持一致。

本次结论是源码层面的可行性判断；并未证明现场所有设备在通信失败、并发和停止条件下已经满足上述要求。
